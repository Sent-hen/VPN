# Threat model

This is a personal VPN: one person's devices talk to one server that person
controls. It provides **privacy on untrusted networks, not anonymity**. It
moves trust from the local network and ISP to the cloud host and to me.

## Assets

| Asset | Where it lives |
|---|---|
| Contents of my traffic | Encrypted between device and server; plaintext after the server |
| Which sites I visit (DNS and IPs) | Visible to the server and to sites; hidden from the local network and ISP |
| Device private keys | Generated on the device; never sent anywhere |
| Server private key | Generated on the server at first boot; never in Terraform state |
| Hetzner API token | Environment variable on the machine that runs Terraform |
| Admin SSH key | Deploying machine |

## Adversaries and what the VPN does about them

### Protects against

- **Someone on the same Wi-Fi** (café, airport, hotel). They see only UDP
  packets to one IP address. Contents, destinations and DNS lookups are
  encrypted by WireGuard (Noise IK, ChaCha20-Poly1305).
- **The ISP or network operator.** Same view as above: "this device talks to a
  Hetzner IP."
- **DNS tampering on the local network.** DNS goes through the tunnel to the
  server's own validating resolver (Unbound with DNSSEC), not to the resolver
  DHCP handed out.
- **IPv6 leaks.** The tunnel carries IPv6 (`::/0` is routed through it), so a
  dual-stack network cannot bypass it over IPv6.
- **Traffic escaping while the tunnel is down.** Planned client kill switch
  (Phase 3). Until then, WireGuard for Windows blocks untunneled traffic when a
  config routes `0.0.0.0/0`, which the generated configs do.
- **Internet scanning of the server.** Only the WireGuard UDP port is open to
  the internet. WireGuard does not respond to unauthenticated packets, so the
  server is silent to scanners. SSH is limited to listed admin networks, or to
  the tunnel only.

### Does not protect against

- **The cloud provider.** Hetzner controls the hypervisor and could read
  memory or disk. Choose a provider whose jurisdiction and policies you accept.
- **The server itself, if compromised.** It sees all traffic in plaintext after
  decryption (HTTPS still protects content). Mitigated by a minimal attack
  surface, automatic security updates, and easy rebuilds.
- **Websites identifying me** by login, cookies or browser fingerprint.
- **Malware on the device.** It runs before encryption.
- **Traffic correlation** by an adversary watching both ends. A single-hop VPN
  with one user offers no anonymity set. Use Tor if that matters.
- **Legal compulsion.** The server's IP is tied to my Hetzner account.

## Design decisions driven by this model

- **No home-made cryptography in the product.** WireGuard is small, formally
  analyzed, and in the Linux kernel. The from-scratch tunnel (Tier B) is
  educational only.
- **Keys are generated where they are used.** Device keys come from `vpnctl
  keygen` on the device; only public keys go into `terraform.tfvars`. The server
  key is generated by `vpn-bootstrap` on the server. Terraform state therefore
  holds no private keys.
- **Peer isolation.** Clients can reach the internet but not each other, so a
  compromised phone cannot scan the laptop.
- **No traffic logs.** WireGuard keeps no connection logs. Unbound runs with
  query logging off.
- **Two firewall layers.** Hetzner's cloud firewall and nftables on the host
  apply the same rules, so one misconfiguration does not expose the server.
- **Rebuild, don't patch by hand.** The server is defined entirely by code and
  can be destroyed and recreated in minutes.
- **Privilege separation (planned).** Only a small daemon runs elevated; the UI
  talks to it over an authenticated local named pipe.

## Known weaknesses and open items

- **SSH trust on first use.** `vpnctl client-config` accepts the server's SSH
  host key the first time it connects. An attacker on the deploying network at
  that exact moment could impersonate the server and hand back their own
  WireGuard public key. Fix: publish host key fingerprints through the
  provider console or pre-generate them (roadmap).
- **Device keys are stored unencrypted** in `%LOCALAPPDATA%`, protected only by
  the user profile's file permissions. Move to DPAPI or Credential Manager in
  the daemon phase.
- **Generated client config files contain the private key.** Delete them after
  importing.
- **The admin account has passwordless sudo.** It has no password and only
  accepts a key, but anyone holding that key controls the server.
- **No post-quantum protection.** Recorded traffic could be decrypted later if
  Curve25519 is broken. A WireGuard pre-shared key would mitigate this
  (stretch goal).
- **Automatic reboots** at 04:00 (server time) for kernel updates briefly drop
  the tunnel.
